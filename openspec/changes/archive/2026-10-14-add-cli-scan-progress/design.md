# Design

## Context

См. proposal.md. `trawler_cli:do_scan/1` использует синхронный API и таблицу всех результатов. Ядро уже предоставляет асинхронные события и статус. Изменение остаётся в CLI и его тестах.

## Goals / Non-Goals

Goals: поток находок без накопления результатов в текстовом режиме; видимая активность во время ожидания, неизменная машинная схема.
Non-Goals: изменение публичного API, сетевых исходов, сортировки JSON, определения сервисов, ETA или объявление хоста отсутствующим.

## Decisions

- JSON остаётся на `trawler:scan/3`, существующей сортировке и `print_json/2`. Флаги `--verbose` и `--no-progress` допустимы рядом с JSON, но не меняют его поведение.
- Текст вызывает `trawler:start_scan/3` с прежними опциями. Получатель и владелец — CLI; `trawler:status/1` возвращает total. Существующие контракты неизменны: `{result, Result}`, `{done, Summary}`, `{cancelled, Summary}`, `{error, Reason, Summary}` в `{trawler, Ref, Event}`. Результаты содержат ip/port/state/elapsed_ms, сводка total/completed/counters/elapsed_ms.
- Состояние CLI содержит Ref, total, локальные completed/counters, монотонные start/next_update, режим progress (tty/plain/off), verbose, признак напечатанного заголовка. Не сохранять список текстовых результатов. Локальные счётчики считают полученные события, чтобы статус ядра не приводил к двойному счёту. Завершающая сводка авторитетна.
- Период: tty 250 мс, plain 2000 мс; начало и финал обязательны. Receive after вычисляется от абсолютного next_update, и срок проверяется также на каждой обработке результата: бесконечный поток сообщений не должен откладывать обновления. Обновление идёт даже без новых результатов. Не создавать отдельный процесс прогресса или неограниченную очередь таймеров.
- Проверить штатный OTP 27 способ определения терминала именно stderr; при недоступности — безопасный plain. В tty очищать текущую строку перед результатом, затем перерисовывать прогресс; stdout и stderr раздельны. Не использовать shell или TERM как единственное доказательство tty. Plain не содержит CR/ANSI.
- Вывод по-русски: «Проверено …/… (…%) | открыто … | … с»; сводка «Завершено», «Открытых портов не найдено», «Закрыто», «Без ответа (таймаут)», «Недоступно», «Ошибки». Строки результата сохраняют state-токены open/closed/timeout/unreachable/error для --verbose и простого поиска. Находки в порядке получения без дублирующей финальной таблицы.
- Начало печатать только после успешной валидации/старта. Для done завершить прогресс и печатать сводку (код 0); error/cancelled завершить строку, сообщить диагностику (код 1). Если `status` возвращает not_found во время работы, закончить прогресс и сообщить ошибку, не зависать. При ожидании периодически контролировать доступность статуса (включая --no-progress); не трогать чужие сообщения.
- Не менять supervision/лимиты/валидацию/сокеты: уход CLI прекращает работу по существующему мониторингу владельца. Новые флаги обрабатываются без создания атомов, повтор запрещён.
- Проверки: CT loopback (открытый локальный сокет, закрытый порт), раздельные потоки, полный JSON, verbose, no-progress, неверные флаги. Для воспроизводимого медленного пути и timeout без внешней сети использовать локальный тестовый драйвер, запускающий реальный CLI с контролируемыми библиотечными событиями (не production-переключатель), либо локальную воспроизводимую задержку. Проверить heartbeat без событий и во время непрерывных результатов, чистую терминальную строку через PTY, отсутствие списка timeout-IP, завершение ошибок.

## Risks / Trade-offs

- Изменение текстовой таблицы → документировать --verbose и стабильный JSON.
- Отдельные stdout/stderr могут отображаться с разным буферизованием → явное очистка/перерисовка; PTY-проверка.
- Живой вывод не сортируется → сохранить сортировку только JSON.
- Таймаут относится к пробе, не хосту → названия сводки и README не утверждают отсутствие компьютера.
